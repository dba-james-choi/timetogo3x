# 운영 노트

이 프로젝트를 다시 만지기 전에 알아두면 좋은 세부사항들.

## 데이터 갱신 스케줄 (DST 대응)

`.github/workflows/update-data.yml`의 cron이 하루 두 번(`15 20 * * 1-5`, `15 21 * * 1-5`)
걸려 있는 이유: 미국 정규장 마감이 UTC 기준으로 계절에 따라 달라지기 때문.

- EDT(서머타임, 대략 3월~11월): 마감 20:00 UTC → `20:15 UTC` 실행이 "진짜" 갱신
- EST(서머타임 해제, 대략 11월~3월): 마감 21:00 UTC → `21:15 UTC` 실행이 "진짜" 갱신

매번 두 번 다 실행되지만, 이미 최신 데이터면 `git diff` 결과가 없어서 커밋 없이 조용히 끝남
(`update-data.yml`의 "Commit and push if changed" 스텝 참고). 그래서 둘 다 걸어놔도 중복 커밋은
안 생김. 정확한 DST 전환일까지 맞추려 하지 않았고(매년 날짜가 바뀜), 단순히 이중 스케줄로
우회한 것 — 필요 이상으로 정교하게 만들지 않음.

## GitHub Actions 60일 비활성화 규칙

GitHub은 저장소에 60일간 활동(push)이 없으면 예약된(cron) 워크플로우를 자동으로
비활성화한다. 이 프로젝트는 거래일마다 데이터가 바뀌어 거의 매일 커밋이 발생하므로
정상 작동하는 한 이 문제는 사실상 발생하지 않는다 (워크플로우 자신의 커밋이 활동으로
카운트되어 계속 리셋됨).

혹시 워크플로우가 오래(수 주 이상) 실패해서 비활성화된 경우:
- 그냥 커밋을 push하는 것만으로는 **다시 켜지지 않는다** (workflow_dispatch 트리거까지 막힘)
- GitHub 저장소 → Actions 탭 → 해당 워크플로우 → 비활성화 배너에서 **"Enable workflow"를
  직접 클릭**해야 함
- 현재 사용 가능한 GitHub MCP 도구 중에는 이걸 대신 눌러줄 수 있는 기능이 없음 — 이 경우엔
  사용자가 직접 클릭해야 한다

## RSI 계산

`scripts/fetch_data.py`의 `calculate_rsi()`가 Wilder's smoothing 방식으로 RSI(14)를
계산해서 각 캔들에 `rsi` 필드로 저장한다 (14개 미만 워밍업 구간은 `null`). 화면에는
1개월(`KEEP_DAYS=35`)만 잘라서 보여주지만, RSI는 그보다 훨씬 긴 원본(`RANGE`) 데이터로
먼저 계산한 뒤에 잘라내므로, 화면에 보이는 첫날부터 RSI 값이 이미 채워져 있다 (워밍업
구간이 화면 밖에서 소비됨). 이 순서를 바꾸면(트림 후 RSI 계산) 화면 앞부분 RSI가
비어버리니 주의.

## SMA200 (200일 이동평균선) 계산

RSI와 같은 패턴. `calculate_sma()`가 단순이동평균(직전 200개 종가의 평균)을 계산해서
`sma200` 필드로 저장한다 (200개 미만 워밍업 구간은 `null`). 화면에 보이는 1개월(~24
거래일) 전체에 값이 채워지려면 그보다 200 거래일 이상 앞선 데이터가 필요해서, 이 지표를
추가하며 **`RANGE`를 `"3mo"`에서 `"1y"`로 올렸다** — `"3mo"`(약 60여 거래일)로는 SMA200
자체가 거의 대부분 `null`이 되어버림. `"1y"`(약 250여 거래일)면 화면 구간 전체에 넉넉한
여유(약 25~30 거래일 버퍼)를 두고 커버됨. 프론트(`app.js`)는 메인 가격 차트 위에 보라색
라인으로 겹쳐 그리고, 카드에 "MA(200) $xxx.xx" 라벨도 같이 표시한다.

## 데이터 소스

`scripts/fetch_data.py`는 Yahoo Finance의 **비공식** chart API
(`query1.finance.yahoo.com/v8/finance/chart/...`)를 사용한다. 공식 API가 아니라서 SLA가
없고, 응답 형식이 예고 없이 바뀌거나 일시적으로 막힐 수 있다. 문제가 생기면 워크플로우
실행이 실패로 표시되므로 Actions 탭에서 바로 확인 가능.

## 날씨 페이지 (weather.html)

- 데이터: [Open-Meteo](https://open-meteo.com) 무료 API, API 키 불필요. 예보(`api.open-meteo.com`)와
  대기질(`air-quality-api.open-meteo.com`)이 **별도 엔드포인트**라 `scripts/fetch_weather.py`가
  둘 다 호출해서 시간(`time`) 문자열 기준으로 병합한다.
- 위치: Victoria, BC, Canada 좌표를 `LATITUDE`/`LONGITUDE` 상수로 고정해뒀다 (`fetch_weather.py`
  상단). 다른 도시로 바꾸려면 이 두 값과 `LOCATION_NAME`만 바꾸면 됨.
- 갱신 스케줄: `.github/workflows/update-weather.yml`이 매일 UTC 00:00, 12:00 두 번 실행.
  주식 워크플로우처럼 "마감 직후" 같은 정확한 기준 시각이 없어서 DST 이중 스케줄 같은 복잡한
  처리 없이 단순히 12시간 간격으로만 걸어둠 — 계절에 따라 Victoria 현지 시각이 1시간 정도
  앞뒤로 흔들리는 건 날씨 데이터 특성상 문제 없음.
- 대기질 API는 예보 API보다 지원 기간이 짧을 수 있어서, 24시간/7일 구간 중 뒷부분은
  `pm10`/`pm2_5`가 `null`로 나올 수 있다. 프론트(`weather.js`)는 `null`이면 "-"로 표시.

## 뉴스 페이지 (news.html)

- 데이터: **Google News RSS** (`news.google.com/rss/...`), API 키 불필요. Saanich/Victoria/
  Vancouver는 지역명 검색(`rss/search?q=...`)에 "BC" 지역 한정자를 붙여서 동명이지(예:
  호주 Victoria)를 피한다. Canada는 검색이 아니라 **지역 헤드라인 섹션**(`rss/headlines/
  section/geo/Canada`)을 쓰는데, "Canada"로 단순 검색하면 이 단어가 언급된 아무 기사나
  다 걸려서 실제 "캐나다 주요 뉴스"가 아니게 되기 때문.
- 제목 정리: Google News 제목은 보통 `"헤드라인 - 출처"` 형식이고 `<source>` 태그도 거의
  항상 같이 온다. `clean_title()`이 `<source>` 값을 알고 있으면 그 정확한 문자열만 접미사로
  잘라내고, 없을 때만 범용 정규식(`- 아무거나`)으로 폴백한다 — 정확한 source 없이 범용
  정규식만 쓰면 헤드라인 자체가 " - 단어"로 끝나는 경우 잘못 잘릴 수 있어서 순서를 이렇게
  둠.
- 갱신 스케줄: `.github/workflows/update-news.yml`이 매일 UTC 13:00/14:00 두 번 실행 —
  Victoria 아침 6시가 EDT면 13:00 UTC, EST면 14:00 UTC라서 (업데이트 스케줄 섹션의 주식
  워크플로우와 동일한 DST 이중 스케줄 패턴). 날씨처럼 "대략 아침"이 아니라 사용자가
  명시적으로 "아침 6시"를 요청해서 느슨한 12시간 간격 대신 이 패턴을 씀. 다만 뉴스는
  주가 종가와 달리 계속 살아있는 데이터라, "틀린" 계절의 실행이 그 시점 기준 기사를 커밋한
  뒤 1시간 뒤 "맞는" 실행이 다시 갱신하면서 하루 2번 커밋이 생길 수 있음 — 날씨 워크플로우와
  같은 이유로 문제 삼지 않음.

## 이 환경(Claude Code 원격 세션)에서의 제약

- 이 세션의 네트워크는 화이트리스트된 도메인만 통과하는 프록시를 거치므로, `query1.finance.yahoo.com`이나
  `*.github.io` 같은 도메인에 직접 curl/fetch가 안 될 수 있다. 실제 GitHub Actions 러너는 이
  제약이 없어 정상 동작하니, 로컬(세션) 검증이 막히더라도 워크플로우 자체가 문제인 건 아니다.
